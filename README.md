## Project Overview

A complete **data engineering and analysis pipeline** built on real-world SHM data from 12 laser displacement sensors deployed across three heritage masonry vault structures. Sensors recorded at 15-minute intervals over 11 months, producing ~40,000 timestamped observations per sensor alongside continuous environmental measurements (temperature, humidity, pressure).

The engineering problem driving the pipeline: raw IoT sensor data from structural installations is inherently noisy — transmission failures, voltage spikes, installation geometry artifacts, and environmental interference all contaminate the signal. Extracting structurally meaningful information requires a pipeline that separates physical behavior from instrument noise without discarding real structural events.

This is the second reporting cycle of an ongoing project. The pipeline was designed to run reproducibly on each new monitoring cycle with no structural changes required.

**Monitoring context:** 12 sensors across 3 zones, 2 measurement axes per zone (diagonal = arch deformation, horizontal = lateral wall spread), 11 months continuous, ~3,463 timestamps.

## Pipeline Architecture

```

        │
        ▼

   → Merge 11 monthly files into one unified DataFrame
   → Parse and standardize timestamps

        │
        ▼
02_data_cleaning.ipynb  [fully automated — all 12 sensors in one run]
   → Phase 1: Geometric filter — remove physically impossible values
   → Phase 2: Chauvenet Criterion — remove population-level outliers
   → Phase 3: IQR filter — k-factor auto-selected per sensor
              find_optimal_k() iterates k=1,2,3... and stops when
              elimination % change between k and k+1 drops below 0.2%
   → Export: clean_S01.csv ... clean_S12.csv + cleaning summary table
        │
        ▼
03_statistical_analysis.ipynb
   → Load and merge all 12 clean CSVs
   → Compute full descriptive statistics per sensor
     (mean, std, CV, IQR, percentiles P1→P99 on relative displacement)
   → Generate comparative bar charts and export summary tables
        │
        ▼

   → Pearson correlation: each sensor vs Temperature, Humidity, Pressure
   → Heatmaps per zone and per axis group (diagonal vs horizontal)

        │
```

## Notebooks Guide

---

### `01_data_ingestion.ipynb`

**What it does:** Loads 11 monthly CSV exports from the IoT platform, concatenates into a single DataFrame, parses timestamps, applies sensor anonymization, and exports zone-level and per-sensor partitions.

**What it showcases:** Multi-file ingestion and concatenation; timestamp standardization across files with varying export quirks; structured data partitioning strategy; anonymization pipeline as a repeatable transformation step rather than a manual find-and-replace.

---

### `02_data_cleaning.ipynb`

**What it does:** Applies a three-phase cleaning pipeline to all 12 sensors automatically in a single run. Each phase targets a distinct category of data quality problem:

- **Phase 1 — Geometric filter:** removes readings that violate the physical constraints of the sensor installation (known distance limits). These are hardware failures, not statistical outliers — no threshold tuning required.
- **Phase 2 — Chauvenet Criterion:** removes values whose probability of belonging to the sample population falls below 1/(2n). Sensor-size-adjusted z-score threshold. Removed 0–1.87% per sensor.
- **Phase 3 — IQR filter with automated k-selection:** `find_optimal_k()` iterates k from 1 upward and stops when the percentage change in valid records between consecutive k values drops below 0.2% — the empirically derived stabilization threshold for this dataset. k values ranged from 1 to 5 across the 12 sensors. Removed 0–8.87% per sensor.

**What it showcases:**
- Sequential filter design where each phase has a distinct, non-overlapping purpose
- Automated k-factor selection that formalizes the stabilization criterion mathematically while preserving full transparency in the output log
- Per-sensor individualization without manual intervention — one run processes all 12
- Full audit trail: each phase logs records removed, percentage eliminated, and data quality classification

> The methodology here is what separates an engineering cleaning pipeline from a generic outlier removal script. The sequence and the reasoning behind each phase are documented in the notebook.

---

### `03_statistical_analysis.ipynb`

**What it does:** Loads and merges all 12 clean CSVs, computes descriptive statistics on relative displacement (movement from structural minimum reference), generates comparative bar charts across all sensors, and exports structured summary tables.

**What it showcases:** Relative displacement as the analytically correct variable (not raw absolute laser distance); CV as the cross-sensor comparability metric when absolute scales differ; percentile bands as an operational classification framework — P50 = structural neutral, P95 = operational limit, P100 = historical maximum. All statistical outputs are paired with physical interpretation, not reported as abstract numbers.

---

### `04_correlation_analysis.ipynb`

**What it does:** Computes Pearson correlation between each sensor and three environmental variables. Generates heatmaps per structural zone and per axis group. Produces normalized temporal overlays for visual validation of the correlation results.

**What it showcases:** Correlation analysis framed around physical causation — identifying which environmental driver dominates, distinguishing a real mechanical effect from a statistical artifact (humidity as inverse temperature proxy), and using cross-sensor correlation to identify zones acting as mechanically coherent units. MinMaxScaler normalization to the physical range of each environmental variable (not 0–1) for interpretable overlays.

---

### `05_sensor_individual_analysis.ipynb`

**What it does:** Generates the complete visual suite for each sensor — 6 plots and 1 Excel table per sensor. Runs in single-sensor mode (change one variable) or full batch mode (all 12 sensors, ~84 output files saved to `outputs/figures/{sensor}/`).

**What it showcases:** Parameterized notebook design — no code duplication across 12 sensors; `matplotlib.use('Agg')` for non-interactive batch rendering; per-sensor folder structure as the self-contained unit of analysis (numbers and figures together); distinction between absolute distance and relative displacement maintained throughout all visualizations.

## Key Engineering Decisions

### 1. Three-phase sequential cleaning

Separating geometric, probabilistic, and statistical filters ensures each category of data quality problem is handled by the most appropriate method. A single IQR filter applied blindly would eliminate real structural peak events; Chauvenet alone would miss systematic sensor drift; neither addresses hardware impossibilities. The sequence matters — and it's documented.

### 2. Automated k-factor selection

The IQR multiplier k controls how wide the valid operating range is. Rather than selecting it manually per sensor, `find_optimal_k()` iterates from k=1 upward and stops at the first point where the change in retained records between consecutive k values drops below 0.2%. This threshold was derived empirically: at every manually validated k across all 12 sensors, the change to k+1 was 0.00–0.20%, while the change at k-1 was still meaningful (0.06–6.0%). The automation reproduces the same decisions without manual iteration.

### 3. Relative displacement as the analysis variable

Sensors record absolute laser distance (~12,000–25,000 mm). The structurally relevant quantity is movement relative to the minimum contracted position — so all statistical analysis, percentile computation, and alert thresholds operate on `value - minimum`. Zero means most contracted state; any positive value is displacement from that baseline.

### 4. Per-sensor independence in cleaning

Each sensor's cleaning parameters (k-factor, Chauvenet threshold) are computed independently from its own data. A single global filter would over-clean sensors with tight distributions and under-clean sensors with wider ones. The 12 sensors have different installation geometries, data quality histories, and structural roles — they should not be forced into a common cleaning boundary.

### 5. S09 as reference node, not excluded

S09 (Zone C diagonal) had 71.45% of values removed due to connectivity failures, leaving only 28.18% valid data. It was not excluded from the dataset — exclusion would silently remove a measurement axis and create an incomplete picture. It was explicitly classified as a **reference node**: retained for directional symmetry checks, flagged in all outputs, and excluded from primary statistical conclusions. The distinction between "excluded" and "reference-only" has engineering meaning and is documented in the pipeline.

## What This Project Demonstrates

- **End-to-end data pipeline engineering:** raw IoT CSV ingestion → multi-phase cleaning → statistical analysis → correlation analysis → per-sensor visual output → structured report
- **Domain-informed methodology:** every pipeline decision is grounded in the physical context of the measurement — not applied as a generic data science template
- **Automated reproducibility:** the full pipeline runs on a new monitoring cycle without structural changes; `find_optimal_k()` adapts per-sensor without manual tuning
- **Statistical-to-physical translation:** Pearson r, IQR, CV, and percentile bands are always interpreted in terms of structural behavior — never presented as numbers in isolation
- **Scalable parameterized design:** single `sensor` variable controls all per-sensor analysis; batch mode processes all 12 without code duplication
